# Poll a Server Action to detect Booking confirmation, not a direct client fetch or SSE

`/bookings/[id]` (`page.tsx`) can render for a Booking still `status: 'pending'` immediately after the Stripe redirect back, before the confirming webhook (#32) has landed. To close that out into "Booking confirmed" without the Guest manually refreshing, a client component (`PendingBookingWatcher`) polls a new Server Action, `checkBookingStatus` (`bookings/[id]/_actions.ts`, a thin wrapper around the existing `fetchBooking`), every 3 seconds, and calls `router.refresh()` once the status flips — re-running the Server Component so the confirmed view renders from freshly fetched data rather than being duplicated in the client component. Polling gives up after ~20 checks (~60s), swapping to a "taking longer than expected" message rather than polling an abandoned tab indefinitely.

The client can't call Express directly to run this check — Express is only ever reached server-side (ADR-0002) — so a Server Action is the hop, the same pattern `book/_actions.ts` already uses for booking creation. A blind `router.refresh()` on a timer (skipping the status check) was considered and rejected: it would re-render the whole page every 3s regardless of whether anything changed, instead of a cheap status read. Server-Sent Events/push was also considered and rejected as real persistent-connection infrastructure (an SSE endpoint, a subscriber registry keyed by Booking id) for a wait that normally resolves in 1-2 seconds — out of proportion to what it solves, and avoided for the same "no new infrastructure to operate" reasoning ticket #30 already applied to reclaiming abandoned holds without a scheduled job.

Getting the webhook to actually fire locally while building this surfaced an unrelated but easy-to-hit gotcha: `packages/api` runs on Bun, and Bun only exposes `crypto.subtle` asynchronously — Stripe's SDK detects that and falls back to its `SubtleCryptoProvider`, under which the sync `stripe.webhooks.constructEvent(...)` (what Stripe's own docs and most examples use) throws `CryptoProviderOnlySupportsAsyncError` rather than working. `PaymentProvider.verifyWebhookSignature` (`payments.ts`) is `async` and uses `constructEventAsync` for this reason, regardless of runtime — a future port to Node wouldn't need to revert it, since `constructEventAsync` works under both.
