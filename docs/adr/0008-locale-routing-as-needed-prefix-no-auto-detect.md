# French i18n nests the app under `app/[locale]`, with an as-needed prefix and no browser-language auto-detect

Adding French support via `next-intl` requires every route to live under an `app/[locale]/...` dynamic segment — there's no way to add App Router locale routing without this restructure. `localePrefix` is set to `as-needed` rather than `always`: English, as the default locale, keeps every URL exactly as it is today (`/about`, `/search`, `/[city]/stays`), unprefixed; only French gets a `/fr/...` prefix. The alternative — prefixing every locale including English (`/en/about`) — would change every URL this site has already had indexed by search engines and shared/bookmarked by users, which cuts directly against this doc's own SEO priorities for no functional gain.

`localeDetection` is disabled, so `next-intl`'s middleware never auto-redirects a visitor based on their browser's `accept-language` header. A visitor reaches French only through an explicit `/fr` URL or the locale switcher (added to the header). This avoids two failure modes of auto-detection: a visitor whose OS/browser is set to French but who wants to browse in English being redirected against their wishes, and search-engine crawlers being redirected away from the canonical unprefixed URL they were trying to index.

Only static UI copy (nav, labels, buttons, form/validation text, legal pages, amenity display labels) is translated under this decision. Listing/Booking data — titles, city/country names, prices, dates — is excluded; it stays exactly as stored, since it's data rather than UI copy and has no translation source. Machine-translating host-written Listing content (titles, descriptions, house rules) via DeepL, as `SYSTEM-DESIGN.md` also describes, is out of scope here: the `description`/`house_rules` fields and the host-authoring flow that would produce them don't exist anywhere in the schema or app today, so there's nothing to translate yet — that remains a separate, future feature.

French translations for `messages/fr.json` are drafted directly by whichever agent implements this feature, rather than left as placeholders for a professional translator. `SYSTEM-DESIGN.md`'s "manually translated and stored per-locale" describes the mechanism (static files, not a runtime translation call) rather than mandating a human translator specifically — there is no translator in this pipeline, so the implementing agent is the one authoring the initial copy, correctable like any other content afterward.

This feature and the pre-rendered city landing pages ([issue #35](https://github.com/immyweb/travel-booking/issues/35), tickets #36/#37) can be built in either order — they don't block each other — but whichever lands second must adopt the `app/[locale]` structure the other didn't yet have.
