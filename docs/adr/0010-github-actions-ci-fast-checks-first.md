# GitHub Actions CI covers lint/format/typecheck/unit+integration tests first; build and E2E are a deferred follow-up

`.github/workflows/ci.yml` adds five independent jobs — `lint`, `format-check`, `typecheck`, `test-web`, `test-api` — triggered on PRs targeting `main` and on pushes to `main`, with `concurrency: cancel-in-progress` so a new push supersedes an in-flight run rather than queuing behind it. The five run as separate parallel jobs rather than steps in one job specifically so that, e.g., a lint failure doesn't hide a typecheck failure behind it — one push surfaces everything wrong at once. This repo previously had no CI at all.

`build:web` and `test:e2e` are deliberately excluded from this first workflow, not merely postponed for convenience: `/[city]/stays` uses `generateStaticParams`, which fetches from the live Express API at build time and fails the build outright if that fetch fails ([ADR-0007](0007-pre-rendered-city-landing-pages-separate-from-search.md)). That means `build:web` needs the same build-a-server/start-a-server/reach-a-database topology `test:e2e` already needs, not the cheap standalone step it looks like at first glance. Rather than build that infrastructure twice — once cut down for `build:web` and once properly for E2E — both are deferred to a single follow-up workflow.

`test-api` runs Postgres as a native GitHub Actions `services:` container using the same image `docker-compose.yml` uses locally (`imresamu/postgis:18-3.6-alpine3.22`, health-checked the same way) rather than shelling out to `docker compose up` — `docker-compose.yml` exists for local dev's `db:up`/`db:down` convenience, not as something CI is obliged to invoke verbatim. Because a fresh container has no schema, the job runs `db:migrate` before tests, mirroring the same step local setup already requires (see README). The job also writes `.env` and `packages/api/.env.test` inline from literal values in the workflow YAML rather than via GitHub Secrets — everything in them (a dummy Resend key, a placeholder Better Auth secret, default `postgres`/`postgres` credentials) is already a non-sensitive test fixture, matching `.env.example` and the (gitignored, uncommitted) `.env.test` used locally, so secrets management would add process for no security benefit.

Bun is pinned to an exact version (`1.3.14`, matching local) rather than tracking `latest`, so a new Bun release can't change CI's behavior on a run that touched no repo code. `bun install` output is cached via `actions/cache` keyed on `bun.lock` — `oven-sh/setup-bun`'s own caching only covers the downloaded Bun executable, not install output.

Branch protection on `main` (making these checks required for merge) is explicitly out of scope here — the workflow ships and reports first; requiring it is a deliberate follow-up once the job names and timing have been proven out by real runs, since turning on required-checks before that risks locking out merges over something as small as a typo'd job name.
