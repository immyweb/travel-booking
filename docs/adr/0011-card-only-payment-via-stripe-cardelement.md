# Booking payment switches from Stripe PaymentElement to CardElement, card-only

Booking payment (`PaymentStep.tsx`, built in #33) moves from `PaymentElement`'s multi-method accordion — Card, Bancontact, EPS, Link, selected automatically from the Stripe account's enabled methods — to a single `CardElement`, and the backend's `createPaymentIntent` (`packages/api/src/payments/payments.ts`) now explicitly sets `payment_method_types: ['card']`. This is a deliberate narrowing, not just a UI change: non-card methods aren't available in any form after this, rather than being preserved alongside a simplified card field. The confirm call also moves from `stripe.confirmPayment({ elements, confirmParams: { return_url } })` to `stripe.confirmCardPayment(clientSecret, { payment_method: { card } })`, which resolves in JS on success rather than redirecting via `return_url` — `PaymentForm` (still on the booking-creation page, `/listings/[id]/book`) now navigates to `/bookings/[bookingId]` with `router.push` itself instead.

The trade is for a shallower DOM: `PaymentElement` renders its card fields inside a nested `elements-inner-accessory-target` frame only after the "Card" tab is expanded, which made Playwright's frame-hunting in `packages/e2e/src/fixtures.ts` fragile; `CardElement` mounts exactly one iframe directly into its own container. Stripe Checkout (a fully-hosted, redirect-away payment page) was considered and rejected as the alternative that would have gotten to zero Stripe iframes on the page at all — but it would have discarded the custom `PaymentStep` / "Confirming your payment…" pending-state UX built in #33 for a bigger UX change (leaving the site entirely) than this decision calls for.

`CardElement`'s default postal code field is hidden (`hidePostalCode: true`) — the booking form doesn't collect a billing address anywhere else, so AVS verification wasn't available in a meaningful form regardless.
