# MSW is the frontend's network-mocking boundary; the backend keeps SDK-boundary mocks

`packages/web`'s Vitest suite adopts MSW (`msw/node`'s `setupServer` — both packages' test runtimes are Node/Bun and jsdom, never a real browser, so `setupWorker` never applies) as its default network-mocking layer, replacing `lib/api.test.ts`'s hand-rolled `vi.stubGlobal('fetch', ...)` + fake-`Response` helper and the `vi.mock('@/lib/api')` used by every other web test file. `server.listen({ onUnhandledRequest: 'error' })` / `resetHandlers()` / `close()` are wired globally in `src/vitest.setup.ts`, backed by a shared happy-path handler set in `src/mocks/handlers.ts` with `server.use()` overrides for edge cases; the `next/headers` cookie-store fake `lib/api.test.ts` already needed (real request scope isn't available under Vitest) is promoted alongside it so any test calling through the real `lib/api` gets working cookies. The practical effect: component and server-action tests now exercise the real `lib/api` implementation with only the network intercepted, rather than a hand-mocked return value — a genuine increase in what each test covers, not just a mocking-library swap.

`packages/api` is deliberately excluded. Its one outbound HTTP call (Resend) is already isolated via a `Mailer` port + `FakeMailer` for route-level tests, and via `vi.mock('resend')` in `mailer.test.ts` to test `createResendMailer`'s own translation logic (idempotency key, error-to-throw). Replacing that SDK-level mock with an MSW handler on Resend's actual HTTP endpoint would trade a small, controlled mock for hand-modeling a third party's undocumented wire format — a real cost with no corresponding gain, since nothing else in the backend makes an outbound HTTP call for MSW to attach to. If a future integration needs it, MSW can be adopted there on its own merits.
